### 1. 分析：UI 自动化测试到底在测什么

UI 自动化的本质是**模拟真实用户**，在真实设备 / 真实浏览器上完成"打开 → 操作 → 看到正确结果"的闭环。它要解决的不是单元测试解决不了的问题，而是：

- **集成回归**：业务流程跨页面、跨进程，单元测试覆盖不到。
- **黑盒视角**：以"用户能看到什么、能点到什么"为唯一可信源。
- **跨平台一致性**：同一业务在 APP 和 H5 上表现是否一致。


> **"用户能看到的 = 测试能断言的；用户能点到的 = 测试能驱动的。"**

所以必须能拿到屏幕画面（screenshot）、必须能拿到 UI 控件树（dump），必须能下发触摸事件（input tap/swipe）。

```

               │        │        │
```

### 3.1 控制器 —— 怎么点、怎么驱动操作，把常用的控制操作都实现，点击，输入，滚动，截图等操作

### 3.2 断言器 —— 怎么验证每一步的正确性

#### 3.2.1 四种断言手段（按可靠性从高到低）

| 类型 | 手段 | 适用 | 实现 |
|---|---|---|---|
| **DOM 断言** | uiautomator XML 中找特定节点 | 原生 APP 主路径 | [PathLocator.exists](file:///D:/UI_Agent/agent/path_locator.py) |
| **Activity 断言** | `dumpsys activity top` 比对前台 Activity | 跳页验证 | [get_current_activity](file:///D:/UI_Agent/agent/adb_controller.py#L233-L242) |
| **文字回读断言** | 输入后读 `text` 值比对 | 表单输入 | [InputAction](file:///D:/UI_Agent/agent/actions.py#L266-L278) |

#### 3.2.2 组合断言策略
每个步骤至少满足以下其一断言即视为通过；**关键步骤要求两条以上**：
```
✅ 必须：操作无异常（subprocess 退出码 == 0）
✅ 必须：截图成功落盘
🔵 推荐：DOM 断言（assertions 列表）
🔵 推荐：Activity 断言（跨页跳转）
```


### 3.3 报告

| 介质 | 路径 | 用途 |
|---|---|---|
| **结构化报告 JSON** | `reports/{flow_id}_{run_tag}.json` | 给 CI / Web Dashboard 用 |
| **每步前后截图** | `screenshots/{flow_id}_{run_tag}/{idx:02d}_{before|after}.png` | 失败回溯、人工复核 |
| **UI XML（可选）** | `screenshots/.../scan_*.xml` | 失败时的 DOM 现场 |


### 3.4 测试场景有一些公共的操作，比如启动APP，截图等操作，进行复用。

UI 一改，**只改字典一行**，所有用到的场景同步生效。

```python
def make_close_popup(name="关弹窗"):
    return CustomAction(name=name, execute_fn=lambda adb, loc: ...)
```

跨场景导入即用，不用每个场景都复制一段"找 X 按钮 + 重试 + 兜底"。



#### 3.5 测试报告的生成，和测试数据清洗

每跑完一次：

- 截图与报告按 `run_tag` 自动归档，不互相覆盖。
- 业务侧脏数据（如测试单据）通过 [mysql_client.py](file:///D:/UI_Agent/agent/mysql_client.py) 在 `teardown` 中按 run_tag/订单号清理。
